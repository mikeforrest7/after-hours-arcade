Visuals manifest — source, capture interface, limitations

Owner: Industrial / game-experience visual designer-worker. Scope: arcade/studio/visuals/ only.

What this is

This directory holds the original cabinet-rendering source and illustrative display composites. The gameplay benchmark release documents the current credited commercial-game screenshots, source boundaries and processing. Furniture studies are not photographs or built products. No game software or extracted game asset is included.

Dependencies for the original cabinet renderer

  • vendor/three.module.js + vendor/three.core.js — Three.js r0.187.0, MIT license (vendor/LICENSE), downloaded from the public npm registry at build time and copied in verbatim. three.module.js imports ./three.core.js by a relative path — keep both files together.
  • No other runtime dependency. No bundler, no CDN script tag, no import map. render.html loads src/main.js as a single <script type="module">.
  • All material/screen textures are generated procedurally on an HTML <canvas> at load time (src/textures.js, src/screens.js, inline canvas helpers in src/decor.js / src/trackballStation.js). No external image files.

Deterministic view / capture interface

Open render.html?view=<name> or call window.setView('<name>') from the console / a capture script. Six views, matching the brief's contract:

view= Shows
hero Three-quarter hero, both stations, both screens lit (flagship framing).
room Pulled-back full room context + the abstract human-scale figure.
trackball Station A control-deck close-up (trackball, 8-button arc, forearm rest).
shooter Station B, handheld holster configuration (two light guns).
mounted Station B, mounted two-axis gimbal alternative (Jurassic Park Arcade style) — deliberately bulkier, post-mounted, olive/gunmetal, never a pistol-grip silhouette.
exploded Station A lifted onto a neutral studio stage, panels separated and labeled (plinth / body shell / face panel / back service panel / deck plinth / control deck).

window.ARCADE_VIEWS lists the six names. window.ARCADE_RENDERER reports 'webgl' or '2d-fallback'. window.renderReady becomes true once the first full frame (3D scene or 2D fallback) has rendered. No continuous animation runs — each view is a single static deterministic render; re-render only happens on a view switch or a window resize. The on-canvas HUD (bottom-left "CONCEPT RENDER" disclaimer, bottom-right view caption) is drawn into the same WebGL canvas via a second orthographic pass, so it survives a canvas-only screenshot as well as a full-page screenshot.

Suggested parent capture filenames

hero.png, room.png, trackball.png, shooter.png, mounted.png, exploded.png — one per ?view= value, screenshotting the <canvas id="scene"> element (or the full viewport; the HUD is baked into the canvas either way).

Four player-experience illustrations

experience-golf.svg, experience-bowling.svg, experience-hunt.svg, experience-jungle.svg — standalone, self-contained SVGs (no external refs). Each shows an abstracted player silhouette actually gripping/aiming the relevant control (trackball spin, handheld gun aim, mounted-gimbal brace), the matching painted screen composition, and a caption block stating plainly that it is original illustrative artwork, not a game screenshot, with support depending on the selected lawful release. These are separate compositions from the in-scene TV textures in screens.js (which show screen content only, no player).

Design limitations (concept-stage, same boundary as the rest of the package)

  • Concept render, not a built product. No part of this scene has been fabricated, photographed or measured against a real cabinet. Dimensions trace to ../../cad/parameters.json (itself concept-stage, not fabrication-ready).
  • Illustrative room, not Mike's basement. 4.5 × 3.5 m / 2.3 m ceiling, per the shared contract — unmeasured.
  • No claim of game compatibility or licensing. Screen art and SVG illustrations are original, stylized compositions evoking golf / bowling / hunting / dinosaur-jungle shooting; they are not reproductions of any specific title's UI, logo or asset, and do not imply a working emulator, donor system or license. See ../../research/game-feasibility.md for the actual evidence boundary per game.
  • Mounted-gun hardware is schematic. The mounted view's two-axis gimbal communicates the shape and scale difference from a handheld gun (bulkier, post-mounted, olive/gunmetal, visible pivot "potentiometer" housings). It is not an engineered mechanism — real potentiometer travel, recoil solenoids, I/O and the required Raw Thrills dongle are explicitly out of scope here (see ../../research/hardware-and-fabrication.md).
  • No VESA/TV-chassis specifics. Wall TVs use the generic active-area trigonometry from parameters.json; actual bezel/VESA pattern is model-dependent and unselected.
  • No real-world lighting/electrical design. Can lights, track lights and sconces are a plausible residential lighting scheme for the render, not an electrical plan.
  • "AFTER HOURS" wordmark is a private working label, not a cleared trademark — shown only as in-scene signage and in the HUD caption, consistent with the brief.
  • Single flagship screen content per station in the 3D scene. Station A always shows the golf composition in-scene (it also hosts Silver Strike Bowling — see the bowling SVG for that pairing); Station B shows the hunt composition except in the mounted view, where it switches to the jungle composition to visually pair control hardware with game. This is a presentation simplification, not a claim about actual shared runtime/software.
  • Abstract scale figure. The room view's human silhouette is a deliberately non-photoreal capsule/sphere mannequin (1.74 m) for scale only — not a character asset.
  • Fallback renderer is a safety net, not a second deliverable. fallback2d.js only activates when WebGLRenderingContext/WebGL2RenderingContext is unavailable; it draws genuine dimensioned 2D plan/elevation diagrams from the same config.js numbers (not a blank page), clearly labeled as a fallback.

Verification performed by this worker

  • All src/*.js files and the vendored vendor/three.module.js / vendor/three.core.js pass node --check (ES module syntax validation).
  • Every exported scene-builder function (buildRoomShell, buildStudioBackdrop, buildDecor, buildFigure, buildTrackballStation assembled + exploded, buildShooterConsole holster + mounted, buildWallTV, buildCableRun, golfScreenTexture/bowlingScreenTexture/huntScreenTexture/jungleScreenTexture, getViewState for all six views) was executed for real in Node with a stubbed 2D canvas context (geometry/material/Object3D construction genuinely runs; only canvas drawing calls are no-ops). This caught and fixed real defects before handoff: Z-up vs. the default Three.js Y-up axis convention on every wall/floor/ceiling/screen/ cylinder orientation (several surfaces — including the TV screens and the room shell — were initially facing the wrong way or lying on their side), a mis-parented speaker position, two Z-centered-vs-bottom-origin coordinate bugs on Station A's back panel, a wall-sconce placement bug that put both sconces outside the room, and an exploded-view stage height that let the dropped plinth clip through the studio floor. Final bounding-box sweep over the fully assembled room scene (155 meshes) shows no NaNs and no unexpected out-of-room geometry.
  • All four experience-*.svg files pass a stack-based XML well-formedness check (every tag correctly opened/closed/self-closed).
  • Not performed by this worker (explicitly out of scope): launching a browser, taking the actual ?view=... screenshots, or any visual/pixel QA of the rendered frames. The parent integration owner runs those checks after these files land, per the brief ("Do not run browser/build/render checks; parent owns those after integration").

Parent integration acceptance

The construction-only checks above were not visual acceptance. The integration owner opened the real Three.js scene in Chromium, confirmed the WebGL renderer (not the fallback), and captured and visually inspected all six views. Final PNGs are 2250 × 1406 pixels from an 1800 × 1125 CSS viewport at the observed 1.25 device-pixel ratio.

Actual rendering exposed defects that construction checks missed: camera and HUD orientation, screen placement and occlusion, text orientation, room-camera framing, exploded-view clipping and backdrop occlusion. Those were corrected before the final captures. The exploded cabinet is an open 18 mm concept shell with a separated control plate; it is still not released joinery or CNC geometry.

All four experience SVGs were rendered. Their 26 text labels had no pairwise text-bound overlap or out-of-viewBox text bounds in the browser audit. Unsupported backswing-meter, offscreen-reload and simultaneous-hunting claims were removed. The mounted-gun view remains a single-mechanism study, not a complete two-player assembly.

The original cabinet-image release used static PNG/SVG images and did not require WebGL to view. Browser and device verification records are retained privately. The newer WebP scene-image release is documented below.

These are original concept illustrations, not photographs, game screenshots, a measured basement survey, or evidence that any requested game runs.

Six golf frames show address, backswing, follow-through, flight, short-shot feedback and putting. Five bowling, four hunting and four dinosaur frames add actual actors, targeting/score information and encounters.

These are other commercial games, not remastered versions of the requested arcade software. Their controls, rules, HUDs and performance are not inherited by this project. Different screenshots can show different sessions, characters and releases; they do not form an uninterrupted captured round.

Processing and interpretive limits

  • Source screenshots are 1920 × 1080 WebP, quality 92. The 2K press image was downsampled from 3840 × 2160; the other frames retain their source dimensions. No upscaling, invented HUD, logo removal or generative alteration.
  • HUD-free promotional screenshots are identified as such; their exact capture mode is unconfirmed. A still does not prove animation quality, responsiveness, frame rate, ray-tracing settings or a working arcade-control mapping.
  • The golf putting image does not establish a holed putt. The bowling lane image is before impact. The four-player bowling screen explicitly says FIRST SHOT; it is not presented as a verified spare attempt. The other score/planning frame carries SECOND SHOT. Captions describe those visible states rather than invent a complete filmed sequence.
  • Arcade walkthroughs distinguish documented controls from proposed cameras and presentation feedback. Modern-game mechanics are not attributed to the arcade originals. Original-release galleries remain available separately.
