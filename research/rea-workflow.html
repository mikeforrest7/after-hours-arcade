REA and open-source software investigation

2026-11-01. Scope: authorized analysis and interoperability research. This is not a game download, a security-device bypass, or proof that four arcade games run.

Tool selected and actual run

The intended project is REA: Reverse Engineer Anything, upstream morluto/rea, MIT license. Its official npm package is rea-agents. A similarly named rea-tools/rea search result returned HTTP 404; it was not used.

  • Official project: https://github.com/morluto/rea
  • CLI/evidence contracts: https://github.com/morluto/rea/blob/main/docs/cli.md
  • Native investigation: https://github.com/morluto/rea/blob/main/docs/native-investigation.md
  • Published metadata: https://registry.npmjs.org/rea-agents/6.8.0
  • Ghidra: https://github.com/NationalSecurityAgency/ghidra
  • MAME debugger: https://docs.mamedev.org/debugger/index.html

Executed: pinned REA 6.8.0 inspect-pe-imports against the already-installed, open-source CPython executable. The target was 106,208 bytes, AMD64 PE32+, SHA-256 4942b86a6597e5aee0128daa00050ed79bc21f6e709a78eb19cbfeb0c2f39ac9. REA returned exit 0, eight imported DLLs and 44 imports; no delayed imports. Full machine-readable result is kept in the project owner's private evidence log, not part of this public package.

This proves one REA static-analysis path executes locally. It did not execute the target, decompile an arcade game, validate USB controls, authenticate a donor system, or exercise Ghidra. Imports do not prove runtime reachability or successful DLL binding; REA records those limitations.

Two runtime issues remain explicit:

  1. Initial inspection of the much larger installed Node executable was refused by REA's default 64 MiB input limit. Selecting the small Python executable resolved that input-size issue; no limit was disabled.
  2. Published REA 6.8.0 requires Node ^22.23.4 || ^24.22.1 || >=26.12.1. The host reports Node 26.7.0. An npm invocation requesting an isolated Node 22.23.4 package still resolved the host Node in a subsequent runtime probe. The successful parser smoke therefore does not certify a supported REA runtime environment. Pin and verify a supported isolated Node executable before real game analysis; do not silently update the Board's shared runtime. No MCP registration, agent restart, binding or global Node change was performed.

No lawful game images, donor hardware, or controller devices were supplied for this project. Game-specific REA runs and emulator play tests cannot be performed from documentation alone. Their inputs and pass conditions are specified below rather than represented by fake results.

Three software paths, kept separate

A. Existing emulation. Best cost path when the exact release is supported and lawful media exists. Freeze the emulator build, selected machine shortname, BIOS/ROM/CHD checksums, input map, display settings and NVRAM. Validate media with the installed emulator's own verifier. A filename match alone is insufficient. Never rely on an internet bundle advertised as containing thousands of games.

B. Original donor electronics. Preferred planning branch for Silver Strike and for modern releases without a proven open-source runtime. Retain the legitimate software, identity/security device, original I/O and required peripherals as a matched system. Rehouse only after it cold-boots and completes a game offline or with its authorized required service. Preserve existing license restrictions and transfer requirements. A loose PC or disk is not a complete kit.

C. Independent implementation. A separate development program, not an emulation shortcut. Observation can inform abstract mechanics and interface specifications, but copied code, models, textures, music, voice lines, proprietary courses, trademarks and bypassed authentication do not become authorized because REA produced them. Where a clean-room process is appropriate, one analyst writes a behavior/interface specification and an independent implementer works only from that specification. Counsel should assess any copying, interoperability exception or circumvention question relevant to the exact jurisdiction and use.

Do not promise a reverse-engineered modern four-game suite for the price of plywood. Physics tuning, content, animation, input feel, device behavior and long-session bugs dominate the work. For a cost-driven personal arcade, use A where proven and B where necessary. Evaluate C only if building games is itself the hobby.

Graph-directed REA runs

For each selected game, preserve a local evidence manifest: title/year/build, acquisition/permission record, artifact SHA-256, architecture, runtime/tool versions, hardware and I/O identifiers, hypothesis, command, output path, limitation and acceptance result. Keep any licensed binaries outside Git and out of agent prompts; tools inspect local files, while the report carries only necessary facts and hashes.

A native REA session uses the documented operations analyze, search, function, decompile, xrefs with --provider ghidra. Select addresses and symbols from the actual inventory; do not fabricate entry points. Retain evidence bundles and query bounded views rather than repeatedly decompiling the same binary. Ghidra setup and architecture support must be proven separately.

No game-run script with invented paths or fake assets is included. Once an authorized local input is available, the agent owns the installation checks and exact, pinned command generation. Persistent REA MCP integration would be a separate home-owned capability admission, not an edit to the personal repo's derived .omp files.

Independent game development scope, if chosen

Golf: relative trackball velocity/direction, swing gesture classification, club selection, ball flight/spin/collision, terrain, camera, scoring, original holes. Bowling: release vector, speed/spin, lane friction/oil model, pin collisions, foul/gutter/reset states and correct ten-frame scoring. Hunting: pump/trigger event ordering, target hit volumes, scoring penalties, spawn paths, timing and original environments. Dinosaur rail shooter: camera rails, two aim streams, enemy behavior, damage, secondary actions, checkpoints and original creatures/assets.

Start with one original playable scene and measured input-to-response behavior. Compare action traces against a written specification, not extracted game content. Gate each additional mechanic on a vertical-slice play review. Estimate effort only after that prototype; this branch is explicitly excluded from the cabinet build schedule and budget.
